## ۱) زمینه و مسئله (Problem Statement)

با رشد تعداد سرورهای کلاستر (سرور اصلی آلمان ۱، سرور ترکیه، و سرور جدید آلمان ۲ با آی‌پی `62.144.51.213`):
1. **تمرکز دیپلوی و آپدیت:** گیت‌هاب نباید مجبور باشد به ده سرور مختلف به صورت تک‌تک SSH بزند. سرور Deploy ما (سرور اصلی Germany 1) باید نقطه مرکزی دریافت کد و ایمیج‌ها از گیت‌هاب باشد.
2. **به‌روزرسانی خودکار و زنجیره‌ای نودها (Cascading Fleet Update):** به محض اینکه سرور اصلی نسخه جدیدی از هسته‌ها، پنل یا کانفیگ را از گیت‌هاب دریافت و با موفقیت مستقر کرد، باید خودکار متوجه شده و سایر سرورهای ورکر موجود در ناوگان را به صورت موازی آپدیت کند.
3. **آمادگی کامل برای سناریوی فاجعه (Disaster Recovery Blueprint):** تمامی سورس‌کدها، پیکربندی‌ها، کلیدها، ساختار دیتابیس و اسکریپت‌های سرور اصلی (Main) باید به صورت ۱۰۰٪ کدگذاری‌شده (Infrastructure as Code) در گیت‌هاب قرار داشته باشند تا اگر سرور اصلی به هر دلیل (تحریم دیتاسنتر، خرابی سخت‌افزاری و...) نابود شد، بتوان هر سرور خام دیگری را در کمتر از ۳ دقیقه دقیقاً به عنوان سرور اصلی جایگزین کرد.
4. **تجمیع کشوری نود جدید آلمان ۲ (`62.144.51.213`):** این سرور باید با مشخصات کامل VLESS Reality، Hysteria 2 و پنل سینک‌شده مستقر گردد و در کلاینت به عنوان پشتیبان کشور آلمان (بدون شلوغ‌سازی منو) برای سوییچ سریع در صورت فیلترینگ آی‌پی اول قرار گیرد.

## ۲) اصول معماری و تصمیمات کلیدی (Key Decisions)

### اصل ۱: سرور اصلی به عنوان هماهنگ‌کننده ناوگان (Main as Fleet Coordinator)
* سرور `86.54.42.124` به عنوان **Main Server (Leader)** ثبت است.
* پایپلاین GitHub Actions (فایل `.github/workflows/deploy.yml`) با هر Push به شاخه `main`، مستقیماً به سرور اصلی متصل شده و نسخه جدید را مستقر می‌سازد.
* سرور اصلی پس از تأیید سلامت کانتینرهای خود، اسکریپت اختصاصی `fleet-update.sh` را صدا می‌زند.

### اصل ۲: به‌روزرسانی زنجیره‌ای نودها (`fleet-update.sh`)
* اسکریپت `fleet-update.sh` روی سرور اصلی لیست سرورهای ورکر فعال را از جدول `servers` استعلام می‌کند:
  ```bash
  SELECT host, domain FROM servers WHERE id != 'srv_main' AND is_active = 1;
  ```
* از طریق کلید SSH مدیریت کلاستر به تک‌تک سرورها وصل شده، دستور دریافت ایمیج‌های جدید GHCR و راه‌اندازی مجدد کانتینرها را ارسال می‌کند:
  ```bash
  ssh root@$worker_ip "cd /opt/ptunnel && ./deploy.sh prod $NEW_TAG $REPO"
  ```
* وضعیت موفقیت نودها بررسی و در لاگ دیپلوی ثبت می‌شود.

### اصل ۳: بازآفرینی صفر تا صد سرور اصلی (Disaster Recovery Blueprint)
برای این که اگر سرور اصلی از بین رفت، بتوان سرور دیگری را به عنوان Main بالا آورد:
1. پوشه `infra/` و اسکریپت `infra/scripts/bootstrap-main-server.sh` به عنوان سورس مرجع نگهداری می‌شوند.
2. اسکریپت با یک دستور تمام پیش‌نیازها، تنظیمات داکر، تمپلیت‌های Xray با روتینگ تحریم، گواهی SSL، سورس کلاینت ادمین و دیتابیس پایه را روی هر سرور جدید ایجاد می‌کند و کلیدهای اصلی (`USER_JWT_SECRET`, `ADMIN_JWT_SECRET`) را تزریق می‌نماید.

### اصل ۴: الحاق سرور جدید آلمان ۲ (`62.144.51.213`)
* مشخصات سرور:
  * شناسه: `srv_germany_2`
  * نام: `Germany 2`
  * کشور: `Germany` (پرچم: 🇩🇪)
  * دامنه: `62-144-51-213.nip.io`
  * پورت‌ها: Reality روی `8080`، Hysteria 2 روی `443` (UDP Hopping: 20000:50000)، پنل روی `8080`.
* تجمیع در کلاینت: طبق ADR-0010، در اپلیکیشن اندروید این سرور در ردیف آلمان ادغام شده و آی‌پی `62.144.51.213` به استخر پروب و نردبان نجات آلمان اضافه می‌شود.
