# ADR-0005 — هستهٔ کلاینتِ مشترک برای اندروید/ویندوز/لینوکس

- وضعیت: **پیشنهادی** (منتظرِ تأییدِ تیم)
- تاریخ: 2026-11-07

## زمینه

اپ امروز به یک AARِ اختصاصیِ اندروید (libv2ray، ۵۸MB) وابسته است. تیم می‌خواهد کلاینت را از نو
بنویسد و همان منطق روی ویندوز و لینوکس هم کار کند، و ترانسپورت‌هایی مثل Hysteria2/TUIC/WireGuard هم
در فهرستِ نامزدها هستند.

## گزینه‌ها

| گزینه | موتور | پوششِ ترانسپورت | چندسکویی | هزینهٔ مهاجرت |
|---|---|---|---|---|
| A | **sing-box** (هستهٔ مشترک) | Reality، Hysteria2، TUIC، WireGuard، SS، ShadowTLS، WS/gRPC | عالی: libbox برای اندروید/iOS + CLI/سرویس برای دسکتاپ | بالا: بازنویسیِ اتصال و پروفایل |
| B | **Xray-core** | Reality، mKCP، WS، SS، XHTTP (بدون Hysteria2/TUIC/WG) | خوب: libXray اندروید + باینری دسکتاپ | متوسط |
| C | ترکیبی: Xray + باینریِ Hysteria | همه | دو هسته، دو کانفیگ، دو مسیرِ خطا | متوسط رو به بالا |

## پیشنهاد

**A) sing-box به‌عنوان تنها هستهٔ محصول**، با یک لایهٔ نازکِ خودمان («Agent») که:
- یک APIِ مستند (JSON-RPC روی localhost یا FFI) برای پوسته‌های UI دارد؛
- پروفایلِ سرور را از پنل می‌گیرد و به کانفیگِ هسته تبدیل می‌کند؛
- منطقِ نردبان/سلامت/تلمتری را **یک‌جا** دارد تا سه پلتفرم سه پیاده‌سازیِ متفاوت نداشته باشند.

دلیل اصلی: خواستهٔ شما «یک بار بنویس، همه‌جا استفاده کن» با یک هستهٔ واحد فقط در حالت A صادق است؛
در C دو هسته یعنی دو برابرِ باگ و دو برابرِ تجربهٔ متفاوت برای کاربر.

## پیامدها

- سرور: Xrayِ فعلی تا پایانِ مهاجرت دست‌نخورده می‌ماند (پروتکل‌ها interoperable هستند). اگر A تأیید شود،
  کانفیگِ سرور هم به sing-box منتقل می‌شود (ADR جدا).
- اندروید: بخشِ کورِ قدیمی حذف و پشتِ یک interface قرار می‌گیرد؛ UI و سرویس باقی می‌مانند.
- دسکتاپ: همان Agent به‌صورت سرویس/TUN اجرا می‌شود؛ UI جدا و نازک.
