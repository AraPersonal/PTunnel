# ADR-0005 — هستهٔ کلاینت: ترکیبی (Xray + Hysteria2) زیر یک Agent

- وضعیت: **پذیرفته** (تصمیم تیم، 2026-11-07)
- تاریخ: 2026-11-07

## زمینه

اپ امروز به یک AARِ اختصاصیِ اندروید (libv2ray) وابسته است. تیم می‌خواهد کلاینت از نو نوشته شود،
روی ویندوز و لینوکس هم همان منطق کار کند، و ترانسپورت‌هایی مثل Hysteria2/TUIC در دسترس باشند.
گزینه‌ها سنجیده شد: sing-box به‌تنهایی، Xray به‌تنهایی، و ترکیب.

## تصمیم

**ترکیب دو موتور، پشتِ یک قراردادِ واحد.** موتورها:

| خانوادهٔ ترانسپورت | موتور |
|---|---|
| Reality، mKCP، WS/TLS، SS، ShadowTLS | **Xray-core** |
| Hysteria2 (QUIC + salamander) | **Hysteria2** |
| TUIC | فعلاً کنار (اگر لازم شد، بعداً) |

لایهٔ میانی `Agent` تنها چیزی است که UI و سرویس با آن حرف می‌زنند:

```go
type Agent interface {
    Start(profile Profile) error   // decides the engine from profile.transport
    Stop() error
    Stats() CoreStats
    Probe(url string) (ms int64)
    State() CoreState
}
```

## چرا این‌طور

- هر موتور در کاری که بهترین است می‌ماند: Xray در Reality/mKCP، Hysteria در QUIC با ماسک و پرشِ پورت.
- یک Agent یعنی **یک** ماشینِ حالت، **یک** نردبان، **یک** تلمتری — سه پلتفرم سه پیاده‌سازی نمی‌شوند.
- مسیرِ پیاده‌سازی: Agent یک ماژول Go است که هر دو موتور را به‌صورت کتابخانه در خود دارد
  (`xray-core` و `apernet/hysteria` هر دو Go هستند)؛ با `gomobile` برای اندروید و به‌صورت
  سرویس/CLI برای ویندوز و لینوکس ساخته می‌شود. اگر embed کردنِ یکی از موتورها دردناک شد،
  فالبک: Agent همان دو موتور را به‌صورت پروسهٔ جدا صدا می‌زند (دسکتاپ) و روی اندروید دو AAR.

## پیامدها

- سرور: کانتینرِ `xray` (Reality + mKCP) و کانتینرِ `hysteria` (QUIC) هر دو بخشی از استک هستند؛
  هر دو با نسخه و digest قفل شده‌اند.
- اپ اندروید: بخشِ کورِ قدیمی حذف و پشتِ `Agent` می‌نشیند؛ UI و سرویس باقی می‌مانند.
- دسکتاپ: همان Agent به‌صورت سرویس با tun؛ UI نازک و مستقل.
- آزمونِ پذیرش هر پلتفرم یکی است: ۲۰۴، ۲۰۰ روی Gemini، و ۸MiB رِنج‌محور کامل.
